# PDF parser evaluation

This measures **parser accuracy**: did Spendly read what is printed on the statement? That is a
different question from the data-quality dimensions on the Data Quality page, which ask whether
the data that was read is complete, valid and consistent. A parser can be 100% accurate on a
statement that is itself missing rows. A statement can reconcile perfectly after a parser misread
a description.

Code: `src/parser_eval.py`. Run: `python -m scripts.evaluate_parsers` (add `--write` to refresh the
table below). Tests: `tests/test_quality.py::test_parser_evaluation_*`.

## Ground truth and matching

Ground truth is what is *printed*: one row per transaction with date, description, direction,
amount and (if printed) balance.

1. Extracted rows are normalised exactly as an import would be. Rejected rows still count as extracted.
2. Expected and extracted rows are aligned **in statement order** with `difflib.SequenceMatcher` on
   (date, direction, amount). Equal blocks pair directly. Replace blocks of equal length pair
   position by position, so a row with a misread date still pairs with its counterpart and counts
   as a date error. The rest are missed (expected) or spurious (extracted) rows.
3. Field metrics use **expected rows** as the denominator, so a missed row is wrong for every field.

| Metric | Numerator | Denominator |
|---|---|---|
| Transaction count agreement | extracted rows = expected rows (yes/no, plus both counts) | – |
| Date accuracy | paired rows with the exact ISO date | expected rows |
| Amount accuracy | paired rows with the exact paise **and** direction | expected rows |
| Description exact | paired rows whose description equals the expected one (after the same masking) | expected rows |
| Description similarity | sum of token Jaccard similarity (unpaired = 0) | expected rows |
| Running-balance reconciliation | consecutive pairs where previous balance ± amount = balance | pairs checked (n/a without a balance column) |

## Fixtures

| Fixture | Layout | Characteristics |
|---|---|---|
| `bank_single_page` | Bank table (Withdrawal / Deposit / Balance) | 12 rows, printed opening and closing balance |
| `bank_multi_page` | same | 140 rows over 3 pages, header repeated on each page |
| `bank_wrapped_description` | same | first narration wraps onto a second line |
| `bank_with_refunds` | same | refund credits mixed with debits |
| `phonepe_no_balance` | PhonePe app statement | 36 rows over 3 pages, transaction IDs, **no** balance column |

These are **synthetic** PDFs generated by `src/sample_pdfs.py` (seeded, reproducible). They imitate
common layouts; they are not copies of a real bank's statement. Because the parsers were written
for exactly these layouts, the results below are an upper bound. They show the parsers and the
evaluator work end to end. They are **not** evidence of real-world accuracy.

**Real statements.** Put consented, anonymised statements in `data/parser_eval/real/` as
`<name>.pdf` plus `<name>.expected.csv` (columns `date,description,direction,amount,balance`). The
folder is git-ignored. Results for real statements are printed locally and never written into this
file. Until representative real formats have been evaluated, Spendly makes no claim about
real-world parser accuracy.

A test tampers with the ground truth (one wrong date, one wrong description, one extra row) and
checks that the metrics drop by exactly those rows. This proves the evaluator can see errors.
